# Jellyfin Administration

Deploy, migrate, upgrade, and troubleshoot Jellyfin servers on the homelab. Jellyfin data is unusually sensitive to *how* it is moved: the SQLite `library.db` encodes absolute media paths, user accounts, and watch state, and the 10.9 -> 10.11 schema migration is a single giant transaction that can wedge for hours.

## 12.0 release + version numbering (Sep 2026)

- Numbering scheme changed: the "10.x" prefix is gone. Feature releases now bump the FIRST number: the 10.12-equivalent shipped as **12.0** (8 Sep 2026), and there will be **no 12.1** — the next feature release is **13.0** (State of the Fin 2026-05 names it as the scanner-rewrite target; mapping is old-minor -> new-major, i.e. 10.13 -> 13.0). Patches continue as 12.0.x. This install is on 10.11.11 (checked live 8 Sep 2026) — a direct 10.11.x -> 12.0 upgrade is supported.
- 12.0 upgrade rules: STOP + full manual backup first (first boot runs one-way DB migrations; `--mode MigrateSystem` runs them without starting the server); remove third-party plugins first (server targets .NET 10, 10.11 builds won't load); a FULL library scan is REQUIRED afterwards and the migration path-checks every item against disk — it will purge this user's deliberately-kept ghost rows, so export the ghost list (Id/Type/Name/Path) BEFORE upgrading. Security fixes included.
- Cadence (GitHub release history): feature-to-feature gaps ran 168/359/323 days (median ~10.6 mo) for 10.9->10.10->10.11->12.0, so 13.0 lands roughly ~mid-2027; first patch after a .0 lands fast (+2 to +19 days historically), then patches every ~1-6 weeks.
- The "Jellyfin release watcher" cron (no_agent script `~/.hermes/scripts/jellyfin_release_watch.py`, state in `~/.hermes/state/jellyfin_release_notified.txt`) emails Paul once per new stable release > 12.0. Retarget to 13.0-only by changing MIN_TARGET in the script.

## Deployment pattern (this homelab)

- **Host**: proxmox LXC (e.g. CT105, unprivileged, Debian 12) with Docker + compose inside.
- **Media**: CIFS shares from proxmox3/4 mounted read-only on the host (`/srv/files/<share>`), bind-mounted into the LXC (`mp0: /srv/files/dguh,mp=/mnt/media`), then bind-mounted into the container as read-only volumes.
- **GPU**: pass `/dev/dri/renderD128` through LXC config AND compose `devices:`; verify the log line `VAAPI device "/dev/dri/renderD128" supports Vulkan DRM interop` at startup.
- **Transcode scope**: this user runs films-only (no music library access). Honor that when deciding what to migrate.

## Library path mapping (CRITICAL)

The DB stores media items at the *old container's* internal roots (e.g. `/data/movies/...`, `/data/tvshows/...`). On the new host you must reproduce those exact paths with compose bind maps, e.g. `/mnt/media/videos/Films:/data/movies:ro`. Get the mapping wrong and every item points at nothing.

Do NOT rewrite paths in the DB unless you must (e.g. film-noir category collapse). Path rewrite in SQLite is viable but the filmnoir nested-folder case needed care; prefer matching the compose map to the DB paths.

## The 10.9 -> 10.11 DB migration wedge (read references/jellyfin-db-migration-10-11.md)

Symptom: server boots, logs `MigrateLibraryDb: Migrating the userdata from library.db may take a while`, then runs 2+ hours at ~50% CPU with the API down; container looks "healthy" to docker but health checks stop logging.

Root cause found on this install: a 1.6 GB `library.db` with **463K items of which ~390K (84%) were music** (Audio/MusicArtist/MusicAlbum/MusicGenre). EF migrates every row in ONE uncommitted transaction; the working set exceeds a 2-core CT's RAM cap and .NET GC-thrashes forever.

**Fix: prune BEFORE migrating.** Remove music (or any unwanted library type) rows from the *copied* library.db, clean orphaned link rows, discard the wedged WAL, restart. Migration then completes in seconds. Full recipe in the reference.

## Diagnosing a wedged migration

- **Progress meter = WAL growth**, not log lines. `stat -c%s jellyfin.db-wal` twice 3-5 min apart: 0 KB/s while CPU is pegged = wedged (GC-thrash), not working.
- `BaseItems` count 0 in the target DB means the giant transaction never committed — killing it loses ZERO progress and is safe.
- When the CT is CPU-starved, `pct exec` hangs. Probe SQLite from the host rootfs instead: `sqlite3 "file:/var/lib/lxc/<id>/rootfs/opt/jellyfin/config/data/jellyfin.db?mode=ro"`.
- Log silence + Kestrel heartbeat warnings + resumed health checks later = thread pool starvation windows around the big save.
- GC-thrash signature: hot `.NET` threads, VmRSS at cap + VmSwap hundreds of MB, host load average inflated.
- RAM bump (4G->6G) helps marginally but is NOT the fix when the row count is the problem. Reduce rows.

## Pitfall: tar ownership clash after appdata move

Extracting appdata as root (pct exec tar) over a compose-prepared config tree leaves root-owned files the container user cannot write — crash loop with `UnauthorizedAccessException: ... plugins/<Name>/meta.json is denied`. Fix: with the container stopped, `chown -R 100000:100000` the config+cache dirs *from the host* (unprivileged LXC: host uid 100000 = CT root = container user). Then `docker compose up -d`.

## Pitfall: media mounts appear empty right after CT boot

CIFS bind mounts inside the LXC take a few seconds to remount at CT start; docker can start before them and create empty `/data/*` dirs. Fix: `docker compose down && up -d` after the mount is live, then verify item counts per library.

## Pitfall: LXC fails to start or hangs at start — suspect the CIFS source before the container

When the LXC's media comes from CIFS bind mounts, a start failure (`pve-container@<id>.service: Main process exited, status=1/FAILURE`) or a foreground `lxc-start -n <id> -F` hanging past 90s usually means the CIFS *source host* is unresponsive, not that the container config broke — nothing inside the guest changed. Diagnose outside-in: `journalctl -u pve-container@<id>.service` for the transition timestamps, then check the source host's load (`uptime`; look for ffmpeg remuxes, dedup scans, `du` walks over multi-TB trees) and write-probe the share. A recovered source boots the unchanged container clean in seconds — that clean boot is the proof the fault was never in Jellyfin. Moving the guest to a bigger host does NOT fix this class of hang: the new guest reads the same CIFS source and stalls identically. Sequence heavy source-host jobs (remuxes, multi-TB rsyncs, full-tree `du`) away from active download/transcode windows sharing the same spindle.

## Verification checklist after a move

1. `docker ps` -> `Up ... (healthy)`; API `System/Info/Public` returns `serverName` + `version` + `startupWizardCompleted: true`.
2. Users preserved: `SELECT Username FROM Users` in jellyfin.db (10.11 schema — no `IsDisabled` column; it has `InternalId`, `EnableAutoLogin`).
3. Item count sanity: `SELECT COUNT(*) FROM BaseItems` matches the pruned source count.
4. Watch state: `SELECT COUNT(*) FROM UserData` non-zero.
5. Libraries: CollectionFolder rows carry *virtual* paths `/config/root/default/<Name>` in BOTH old and new DBs — identical shape old-vs-new proves faithful migration; the real roots live in the compose bind map + LibraryMonitor "Watching directory"/"Skipping ... path does not exist" log lines.
6. Media readable through container: `docker exec jellyfin dd if=/data/movies/<file> bs=1M count=1 | wc -c` > 0.
7. Errors after restart: grep log for `[ERR]`/`[FTL]` since the last clean start.

## Transcode "fatal player error" — three known causes (read references/vaapi-codec-troubleshooting.md)

Cause A — VAAPI encode profile. Symptom: playback dies instantly; the ffmpeg-transcode log ends in `No usable encoding entrypoint found for profile ...` then `Conversion failed!`. Root cause on this install: `encoding.xml` had `AllowAv1Encoding=true`, but the Intel N150 (Alder Lake-N) iGPU CANNOT hardware-ENCODE AV1 — AV1 is decode-only on that generation. Every transcode that selected AV1 died at encoder open.

Cause B — container/extension mismatch (Sep 2026: mkv bytes named `.avi`). Symptom: same player error, but the ffmpeg log ends in `Error opening input: Invalid data found when processing input` (forced `-f avi` demuxer on EBML bytes `1a 45 df a3`). Jellyfin picks the input demuxer from the file EXTENSION, so a Matroska file wearing a DB-expected release name like `Kiss.Me.Deadly.1955.BRRip.XviD.MP3-XVID.avi` always fails — encoder fixes will not help. Rule: the on-disk extension MUST match the real container (check magic bytes: mkv = `1a 45 df a3`, avi = `RIFF`). When the DB-expected name lies about the container, rename the file to its true extension (native write on the SMB server, not via the ro CIFS mount) — do not keep the fake extension to satisfy the DB row. The rename alone is NOT sufficient: the DB row still points at the old name (see Cause C).

Cause C — stale DB path after the container fix (Sep 2026 follow-on to Cause B). Symptom: identical player error persists AFTER the on-disk rename; the newest `FFmpeg.Transcode-*_<itemid>_*.log` now ends in `Error opening input: No such file or directory` on the OLD filename. Diagnosis: `SELECT Path, Size FROM BaseItems WHERE Path LIKE '%<Film>%'` still returns the old path while `docker exec jellyfin ls` shows only the new file. Fix is a staged single-row DB swap — the one sanctioned exception to the never-rewrite-the-DB rule (that rule assumed the DB name was truthful; when it lies about the container, the row must be corrected, not the disk): stop the jellyfin container → timestamp-backup `jellyfin.db` (keep a copy in `/tmp` AND one in `config/data/SQLiteBackups/`) → copy to a staging file → `UPDATE BaseItems SET Path='<new>', Size=<bytes>, DateLastSaved=<now>, Data=json_replace(Data,'$.Container','mkv','$.Size',<bytes>) WHERE Id='<ITEMID>'` → `DELETE FROM MediaStreamInfos WHERE ItemId='<ITEMID>'` → re-INSERT fresh stream rows from container-side ffprobe (`/usr/lib/jellyfin-ffmpeg/ffprobe -show_entries stream=index,codec_type,codec_name,width,height,sample_rate,channels:stream_tags=title,language` — video StreamType=1, audio=0, subtitle=2; note the table has NO `Type`/`DisplayTitle` columns, it uses `StreamType`/`Title`) → `PRAGMA integrity_check;` must return `ok` → swap staged file over live `jellyfin.db`, delete `-shm`/`-wal`, restart container, retry playback. Rollback = restore the backup + restart (~1 min downtime). Never rescan — posters/backdrops/userdata untouched. Always get explicit user approval before the live swap.

Post-swap "still failing" triage — prove the retry reached the server before re-diagnosing. `ls -lat` the log dir: a fresh `FFmpeg.Transcode-*_<itemid>_*.log` must appear for the new attempt, and `grep <itemid>` in the main log should show new TranscodeManager lines. If NOTHING new appears (newest files predate the restart, only old `[ERR]` lines remain), the attempt never left the client — it is holding stale stream URLs for the dead path. Remedy is client-side: hard-refresh the web tab (Ctrl+Shift+R), back out to the film page, press Play fresh (never resume the stalled player), and ask which client (browser/app/TV) plus the exact symptom. Do NOT re-edit the DB or encoder settings on a no-new-logs failure. Note: nginx `connect() failed (111: Connection refused)` lines during the container-restart window are expected noise, not a proxy fault.

Rule: enable hardware codecs in Jellyfin only for what the GPU can actually encode/decode —
decode support does NOT imply encode support. N150: encode = h264 + hevc only; decode =
h264 + hevc + av1. Set `AllowAv1Encoding=false`, `AllowHevcEncoding=true`, keep av1 in
HardwareDecodingCodecs. Probe the GPU with `scripts/vaapi-encode-probe.sh` (inside the
container) before trusting any UI toggle — do not trust a checkbox.

## Judder / jumpy direct-play with no transcode log — check the file's timebase

When playback stutters but no ffmpeg transcode spawns, the defect is in the file or the
delivery path, not the encoder — a direct-play passes file timestamps through bit-for-bit.
Probe the video stream (`ffprobe -select_streams v:0 -show_entries
stream=r_frame_rate,avg_frame_rate`) and compare against a sibling copy when one exists: an
off-spec rate (e.g. 23.975986 instead of 24000/1001) causes even-cadence micro-stutter as the
player periodically re-locks, most visible in long smooth pans. Even cadence = file defect;
bursty smooth-then-stutter clusters = delivery (CIFS/network read stalls on a contended
spindle). Browser clients add their own 23.976-to-60 Hz pulldown judder — compare other 24p
titles in the same client before blaming the file. Fix a bad timebase with a stream-copy
remux on the SMB server itself (native write, never via the read-only CIFS mount — run
detached with a log for multi-GB files, since a foreground remux can saturate a small
source host and stall SSH/CIFS):
`ffmpeg -i src.mkv -map 0 -c copy -video_track_timescale 24000 -r:v 24000/1001 fixed.mkv`.
Verify the fixed file (container ffprobe shows exactly `24000/1001` on both rate fields,
all streams carried, mid-file decode probe `ffmpeg -ss <mid> -i fixed.mkv -t 20 -f null -`
exits 0), then swap it into the exact DB-expected basename — move the original aside as
`.orig.mkv` first, rename the fixed file over it — so no rescan or DB edit is needed.
Confirm through the container path (ffprobe + a small `dd` read under `/data/...`) before
handover; keep the `.orig` backup until smooth playback is confirmed, then delete it.

When the remux still judders, the source encode has uneven packet durations baked in —
only a full re-encode rebuilds even frame pacing. Run `libx264` on the SMB server itself
(native write, never via the read-only CIFS mount): `nice -n 10 ffmpeg -y -i src.orig.mkv
-map 0 -c:v libx264 -preset medium -crf 20 -pix_fmt yuv420p -r 24000/1001 -c:a copy
-c:s copy dst.recode.mkv`, detached with a log (a 1080p feature takes ~10h on a small
Gen8 host, so schedule overnight away from viewing windows). Verify the recode the same
way (exact `24000/1001` on both rate fields, mid-file decode exits 0), then swap it into
the DB-expected basename — move the live file aside as `.remux-backup.mkv`, rename the
recode over it. A DB Size field that still shows a mid-encode value after the swap is
cosmetic (the scanner read the growing file); it self-corrects on the next validation
pass and never affects playback.

## DVD-folder (VIDEO_TS) rows play as a raw VOB chain, not a film

A Movie row whose Path is the FOLDER itself (not a file), whose Size equals the first VOB's byte size, and whose stream rows lead with `dvd_nav_packet` is a DVD-folder ingest — playback serves split 1 GB VOBs with no IFO navigation, so it stutters or stops at file boundaries. That is the file layout failing, not the encoder: do not chase transcode settings for it. Confirm with per-VOB durations (`ffprobe -show_entries format=duration` per `VTS_*.VOB`) and a mid-file decode probe of any sibling playable. Absent ffmpeg logs for the item Id AND absent mentions in the main log means the attempt never reached the server (client-side chain break) — same triage as a no-new-logs post-swap failure. A folder that gained playables after its DateLastRefreshed is blind to them until a library-scoped Refresh of that library only; orphan Video rows whose Path folder no longer exists on disk are dead entries that Refresh correctly purges. If the library-scoped pass leaves the row's DateLastRefreshed untouched, follow with a per-item Refresh on the Movie Id (Recursive=true, MetadataRefreshMode=FullRefresh, both ReplaceAll flags false) — the narrower call re-reads the folder when the broad one skips it.

Completing a partial VIDEO_TS from a pristine second copy: diff the file lists, copy ONLY the missing files host-to-host with a native write on the SMB server (never via the read-only CIFS mount), and md5-verify each arrival against the rip's `.md5` manifest when one ships alongside (scene DVD rips usually carry one in an extras dir with a lineage `.txt` that doubles as a metadata synopsis). Byte-identical shared files mean the copy is incomplete, not corrupt — the signature is missing title-set IFOs (`VTS_0N_0.IFO/BUP` = no navigation for that part) plus missing tail VOBs (truncated episodes). Complete the canonical library copy; never mount the rescue image as a second library source (duplicate rows for the same film, plus loop-mount fragility).

Recode policy for DVD-era material — fix on complaint, not blanket recodes: remux a sibling `.m4v`/`.mp4` to `.mkv` by stream-copy (dropping `mov_text`/`bin_data` streams per the intake rule) so the watchable version is a clean seekable file; recode VOBs (mpeg2 → h264 with deinterlace) only when the DVD cut is actually watched; leave superseded-era XviD rips as alternates untouched.

## Re-created item loses its images — refresh per item, never rescan

Renaming a file to its true container (or any path change the scanner notices) can make
the server DELETE the old row — image rows and orphan poster dir with it — and CREATE a
fresh row (new Id, empty DateLastRefreshed, no provider IDs, zero images). A single-row
path/stream edit never writes image rows or metadata files itself, but expect the item to
go imageless afterward and plan a targeted refresh.

Diagnose before blaming the edit: compare a pre-edit DB backup against live — count
`Movies.Movie` rows with no `BaseItemImageInfos` row in each, then diff the name sets to
isolate newly-imageless from always-imageless (ghost entries without provider IDs never had
posters). Compare by Path, not Name — the same title can be two different rows with two
different Ids. Confirm stale pointers by mapping each image Path (`%MetadataPath%` to the
config metadata dir, `/config/` to the config root) and checking disk existence; rows
pointing at long-gone dirs or stale nested `/data/...` segments predate the session.
Repeated `Could not find file ... folder.jpg/backdrop.jpg` lines for such paths are
cosmetic artwork 404s, not a hang cause.

Remedy is a per-item metadata refresh through the REST API (full refresh with image fetch
enabled) on the affected Ids only — posters re-download without touching anything else.
Never run a full rescan across all libraries: it purges deliberately-kept ghost entries. A library-scoped Refresh (`POST /Items/{libId}/Refresh?Recursive=true` with both ReplaceAll flags false) of the single affected library is safe — it picks up new files while other libraries' ghosts stay untouched; use it for all new-file intake. TV episodes misfiled as Movie rows inherit the series poster — never Apply movie posters to them, so refresh films only.

Batch poster recovery after a re-creation event: mine the pre-event DB backup for provider IDs, not images — old image rows point at dead `%MetadataPath%` hash dirs and stale nested `/data/...` segments, while the old `ProviderIds` (Tmdb/Imdb) are still valid. Drive recovery per item with `POST /Items/RemoteSearch/Apply/{id}?ReplaceAllImages=true` carrying the old IDs, throttled (~1/sec), then re-read `ImageTags` to verify — the endpoint returns an empty 200 even on failure, so trust the re-read, not the status. Verify through the parent listing (`GET /Items?ParentId={libId}&Recursive=true&IncludeItemTypes=Movie&Fields=Path,ProviderIds,ImageTags`, read `ImageTags.Primary`) — the per-item detail call can 400 on field combinations the listing accepts. Apply once more after a few seconds when the first pass lands empty; the image download can race the DB write. Apply fetches art but does not persist the provider link, so keep the old-to-live ID map as a JSON file — re-running the batch from it takes minutes if re-creation recurs. For titles with no old IDs, run read-only `RemoteSearch` trials by name plus year and show the hits for a human pick before applying anything; series-type items are invisible to movie search and need a series-type query instead.

Forensic access: query SQLite from the host rootfs path with Python's sqlite3 over a
`file:...?mode=ro` URI rather than shell-quoted `sqlite3` one-liners (built-in function
support varies by build and quoting breaks) — and never `python3 -c` through SSH either
(nested quotes die with `unexpected EOF`); write the probe to a local `.py` file and feed
it over stdin (`ssh host 'python3' < /tmp/probe.py`). Do not filter library membership by
`ParentId` — items link to their library through the `AncestorIds` table, so a
`ParentId='<libId>'` predicate returns zero rows; filter by `Path LIKE '/data/<lib>/%'`
plus `Type` instead (the CollectionFolder Id can differ in case from the API library id).
When the container host is CPU-starved, `pct exec` hangs — probe from the host instead.

## Clearing a stuck Resume position (UserData)

One item can hold MULTIPLE UserData rows under different CustomDataKey formats (legacy numeric key, lowercase item id, external id) — all pointing at the same PlaybackPositionTicks. Clearing one row leaves Resume alive. Prefer the live REST API — one call clears all key formats for that user+item with no container restart: `POST /Users/{userId}/Items/{itemId}/UserData` with body `{"PlaybackPositionTicks":0}`, authenticated by API key, then verify with `GET /Users/{userId}/Items/{itemId}` plus `SELECT ItemId,CustomDataKey,PlaybackPositionTicks,PlayCount FROM UserData WHERE ItemId='<ITEMID>'` showing 0 on every row. PlayCount and Played flags survive the call — watch history stays. Fall back to SQLite surgery only when the server is down: stop container → timestamp-backup jellyfin.db → `UPDATE UserData SET PlaybackPositionTicks=0 WHERE ItemId='<ITEMID>'` → `PRAGMA integrity_check` must return ok → delete -shm/-wal → restart. Never DELETE the rows — zero the ticks so Played state survives. If the client still offers Resume after the server is clean, the browser cached the position — hard-refresh the web tab and start via Play fresh, never resume the stalled player.

## Downloader queue — an `error`-state torrent blocks slots silently

A torrent in `error` state never auto-retries and keeps holding one of its
`max_active_downloads` slots while doing nothing, so the queue behind it looks stopped.
A transient write-path stall (CIFS source unresponsive) surfaces as a file error naming the
partial file (`... .!qB ... No space left on device`) despite free space on the disk —
recheck/resume the torrent after the path is healthy instead of re-adding it.
`stalledDL`/`forcedDL` at ~0% with zero seeds and dead trackers cannot move client-side;
replace the torrent rather than forcing retries. A complete/seeding torrent is NOT proof of ingestion — audit every complete name against a Jellyfin DB Path/Name row plus the on-disk library copy (size match + decode probe) before deleting its torrent and source files; completed-but-never-ingested files are the normal case after a downloader retarget, and deleting on progress alone destroys the only copy. Search by Name across ALL libraries first — a title can already live under a different library than the one being audited, and ingesting again creates a silent duplicate. Triage recent completions with `GET /api/v2/torrents/info?sort=completion_on&reverse=true` (no auth needed from the whitelisted LAN) — `forcedUP`/`queuedUP`/`stalledUP` at 100% with a real `completion_on` timestamp are done; anything still carrying `.!qB` under `/downloads/temp` is a partial, never a source. For batch ingests, fan out parallel workers that copy+verify and report torrent hash plus delete-readiness, and centralize the actual torrent+file deletes afterwards — only after size match, decode probe, and Jellyfin row all pass.

## Library content audit — ghost items after a move/merge

After migrating, DB items can point at files that do not exist (content never copied off the
old NAS) or at old release-style names (`Alphaville.1965.FRENCH.1080p.BluRay.x265-VXT.mp4`)
while files were renamed clean (`Alphaville (1965).mp4`). Audit DB Paths vs physical files
(see reference below). Empty dirs on BOTH source and destination predate the migration and are
ghosts that can never play — encoder fixes will not help them. Keyword filename searches also catch release-group tags — a `-Noir` / `{1337x}-Noir` suffix marks the pirate group, not the genre; confirm a hit against its DB row before treating it as library content. Repeated `Could not find file ... folder.jpg/backdrop.jpg` lines for stale nested image paths are cosmetic artwork 404s — they never hang the server, so do not chase them as a hang cause. Audit from the host SMB mount
path, not inside the LXC: media bind mounts exist only in the docker namespace (`docker exec`),
not in the CT namespace (`pct exec`).

Ghost taxonomy — query `Type` as well as `Path`: a `Folder`-type row with NULL Size and zero top-level files on disk is a fully-empty ghost; a `Folder` row whose dir holds only `extras/`/`featurettes/`/`interviews/`/`trailers/` subdirs is an extras-only ghost whose main-film `Movie` row is the missing piece. Count top-level files per dir (`find <dir> -maxdepth 1 -type f | wc -l`) alongside the DB query (`SELECT Id,Type,Name,Path,Size FROM BaseItems WHERE Path LIKE '/data/<lib>%'`) so the report separates fully-empty from extras-only instead of lumping both as "empty".

**Chosen remediation (this user, Sep 2026): rename disk files to the DB-expected release
names — never rewrite the DB, and never run a library rescan.** The user keeps ghost entries
as an explicit "films I need to replace" list, so a rescan (which purges them) is off-limits.
Do the renames on the SMB server natively (`/mnt/<share>/videos/...` on proxmox3) — the prox1
`/srv/files/...` view is a read-only CIFS mount and renames fail there. `mv` per dir to the
exact DB basename (release-style names, e.g. FileBrowser download timestamps
`2025-03-16-05-39_265132508.mp4` renamed to the release title). If one disk file maps to two
DB rows (main film + extra), rename to the main row and leave the extra as a ghost. Then
verify DB-path resolution from the host read-only mount, and confirm playback via the API
(see reference). Drop replacement files into the empty ghost dirs later, name-matched to the
DB entries, and they light up without any rescan.

## Password recovery (forgot the admin password)

Jellyfin hashes passwords with PBKDF2-SHA512 — **the original text can never be recovered** from the DB (one-way, salted, 120K-210K iterations). Reset instead; full working recipe in `references/password-recovery.md`.

- Usernames on this install: `root`, `tv`, `emily`, `remote`, `kathleen`. **Admins: `root` + `remote`** (Permissions table: Kind=0 row with Value=1 = IsAdministrator). Users often try guessed names (Paul/Admin/kiwipaul) that don't exist — check the DB list first.
- Hash format (PHC string, **hex** not base64): `$PBKDF2-SHA512$iterations=210000$SALT_HEX_UPPER$HASH_HEX_UPPER` — 16-byte salt, 64-byte derived key, iterations default 210000 (older accounts may show 120000). Verified against source: `CryptographyProvider.cs`, `PasswordHash.cs`, `Constants.cs`.
- Reset procedure: stop container → back up `jellyfin.db` → generate hash (`hashlib.pbkdf2_hmac("sha512", pw, salt, 210000, dklen=64)`, hex upper) → `UPDATE Users SET Password='<hash>' WHERE Username='root'` → start container.
- API login test **requires an `X-Emby-Authorization` header** (`MediaBrowser Client="x", Device="x", DeviceId="x", Version="1.0.0"`); without it the endpoint throws a bare stack trace instead of returning "invalid username or password". Success returns the full User object.
- Backup the DB before the UPDATE (`jellyfin.db.pwreset.bak`) — the reset is the only path, there is no undo.
- After handing a reset password to the user, they may change it themselves. Later API/auth
  tests then fail with "Invalid username or password" — do NOT assume the reset regressed and
  re-reset. Check the auth log for `Authentication request for "root" has succeeded` (their
  new login) and compare the `Users.Password` hash / `jellyfin.db` mtime against your backup
  before touching anything. If API verification still needs to run, **ask the user for the
  new password** (use it transiently, scrub it from test scripts afterward) — never re-reset
  over a password the user has taken over.

## Audio/subtitle defaults — container flags first, user prefs second

How Jellyfin picks the audio track: per-USER language preference (`Users.AudioLanguagePreference`, e.g. 'eng') wins when set; when EMPTY (all 5 users on this install), it follows the **container's default-track flag**. mkv default flags are header bits — flip without remux via mkvpropedit on proxmox3 (installed 6 Sep 2026, v92.0): `mkvpropedit "<file>.mkv" --edit track:a1 --set flag-default=0 --edit track:a3 --set flag-default=1`. Track numbering: `track:aN` = Nth AUDIO track (1-based among audio only — a3 = 3rd audio = index 3 incl. video). Verify with `mkvinfo | grep -E "Track number|Language|Default track"` and container-side ffprobe (`.../ffprobe -show_entries stream=index,codec_type:stream_disposition=default`). Rule for every multi-audio replacement: audit default flags BEFORE handing over — dubs (rus MVO/AVO) often ship flagged default. If a user still gets the wrong track despite correct flags, set their `AudioLanguagePreference`/`SubtitleLanguagePreference` instead of re-flagging. There is no server-global subtitle switch and no trailer exception — subtitle display is per-USER `SubtitleMode` (`Default` follows container default flags, `No Subtitles` never auto-shows, `Only Forced` shows forced foreign-language lines only) plus per-device player overrides that can diverge from the user default. Trailers/extras are ordinary video items, so a releaser-set default sub flag auto-shows under `Default` mode. Prefer `Only Forced` for everyday users; for trailer-only complaints clear default/forced flags on the extras files (`mkvpropedit --edit track:s1 --set flag-default=0 --set flag-forced=0`) instead of changing film behavior. Bulk mode change is per user: `GET /Users/{id}` first, then `POST /Users/{id}/Configuration` (this build accepts POST, not PUT — returns 204) carrying back the FULL Configuration object with only `SubtitleMode` flipped (to `OnlyForced`), preserving every other key — never POST a partial object — then re-GET each user to verify the mode stuck before handover. Send `X-Emby-Authorization` (`MediaBrowser Client="x", Device="x", DeviceId="x", Version="1.0"`) alongside the API key on all `/Users/*` calls.

## Replacement-file intake — container and naming rules

Drop-in replacements for ghost entries must satisfy three checks before handover, in this order. Classify ghost re-enable vs new title BEFORE copying: query Type/Path in the live DB — a Folder-type ghost row with NULL Size means a name-matched drop-in lights up with no scan, while no row at all means a new title needing a library-scoped Refresh of that library only after the copy.

Locate intake sources in the known download dir directly — never full-tree find across multi-TB mounts; the walk stalls past SSH timeouts.

1. **Extension must equal the real container.** Probe the source (`ffprobe -show_entries format=format_name`) and name the destination file accordingly — mkv bytes wearing a DB-expected `.mp4`/`.avi` name re-triggers the Cause-B demuxer failure. A wrong extension copied to the library must be deleted and re-copied with the right one; never leave both.
2. **MP4/M4V sources with `mov_text` subtitles cannot mux directly to Matroska** — the mux fails (`Subtitle codec ... is not supported`, empty output). Remux video + wanted audio only, stream-copy, no re-encode: `ffmpeg -i src.m4v -map 0:v:0 -map 0:a:<wanted> -c copy -disposition:a:0 default dst.mkv` (attached-pic `png`/`mjpeg` and `bin_data` streams are dropped with the subtitle). MP4s carrying an `mjpeg`/`png` attached-pic stream or `und` (untagged) language play as-is but should be offered as a clean-mkv remux: stream-copy video + wanted audio only, drop the attached-pic, and tag the kept streams `eng` (`-metadata:s:v:0 language=eng -metadata:s:a:0 language=eng`). When stream 0 is audio (audio leads video), always map explicitly with the wanted index counted among audio only from a flat probe — never assume the wanted track is a:0; rus-sourced rips routinely put dubs first with the English Original (often mono) last. Then verify with a mid-file decode probe (`ffmpeg -ss <mid> -i dst.mkv -t 10 -f null -`, must exit 0) — a completed copy is not proof of playability.
3. **Audit and set audio defaults immediately after copy** (same mkvpropedit rule as above — dubs ship flagged default), verify byte-identical sizes src vs dst (do the size comparison BEFORE any mkvpropedit flag pass — flag writes shift the file by a few KB), then confirm the DB-expected basename matches exactly so the ghost lights up with no rescan.

Remove the torrent AND its files from the downloader only after all three pass (`POST /api/v2/torrents/delete` with `hashes` + `deleteFiles=true`, then re-list to confirm zero remain) — the library copy is the only remaining instance.

4. **Identify: attach Tmdb/Imdb reference IDs via scripted TMDB lookup, then Apply to fetch metadata.** New rows land with no provider links and no art; clean `Title (Year)` names usually self-identify on the next refresh, but release-style filenames do not — give every new title explicit IDs via the TMDB v3 API (keys stored in `/root/.hermes/.env` as `TMDB_API_KEY` + `TMDB_READ_TOKEN` since 11 Sep 2026, mode 600): (a) `GET https://api.themoviedb.org/3/search/movie?api_key=$TMDB_API_KEY&query=<urlencoded Title>&year=<YYYY>` (key auth) → take the top hit's numeric `id` as the Tmdb id. TMDB search is spelling-sensitive — a British-"s" spelling can return zero hits where the American-"z" spelling returns the full set, so retry with the alternate spelling or a shorter query before concluding no match. Sequels sharing a title each carry their own TMDB/IMDb ids — verify every part separately, never copy Part 1's ids across (Decline trilogy: Pt1 21137/tt0082252, Pt2 Metal Years 36724/tt0094980, Pt3 44848/tt0138393; Pussy Riot: A Punk Prayer (2013) 159032/tt2481238); (b) cross-check with bearer auth `GET https://api.themoviedb.org/3/movie/<id>?language=en-US` (header `Authorization: Bearer $TMDB_READ_TOKEN`) — the `imdb_id` field gives the `ttXXXXXXX`, and `GET .../movie/<id>/external_ids` confirms `imdb_id` + `wikidata_id`; record the verified pair (worked example: Decline of Western Civilization (1981) = Tmdb 21137 + Imdb tt0082252, overview 'The Los Angeles punk music scene circa 1980...', runtime 100, verified 11 Sep 2026 via both auth methods); (c) Write the IDs directly to the item (this is the path that works on 10.11.11 — RemoteSearch/Apply does NOT persist): `GET /Users/{uid}/Items/{itemId}` for the full DTO (bare `GET /Items/{itemId}` 400s), set `ProviderIds={"Tmdb":"<n>","Imdb":"<tt..>"}` + `ProductionYear=<YYYY>` on the full object, then `POST /Items/{itemId}` with the whole DTO back (204; send `X-Emby-Authorization` alongside the key; do NOT touch LockedFields — `ProductionYear` is not a valid MetadataField enum value and 400s the write). Verify the re-read shows the IDs + year, then (d) trigger metadata fetch with `POST /Items/{itemId}/Refresh?Recursive=true&MetadataRefreshMode=FullRefresh&ImageRefreshMode=FullRefresh&ReplaceAllImages=false&ReplaceAllMetadata=false` (204) — after ~25s the server fills Overview + TmdbCollection + Thumb/Logo from the providers. Proven 11 Sep 2026 on the Decline BDRemux item (d6967e56…): direct POST stuck Tmdb 21137 + Imdb tt0082252 + year 1981, Refresh added the punk-scene overview + collection 157671 + Thumb/Logo. RemoteSearch/Apply is a known dead end here (204 + log `Setting provider id's ...: {}` but zero `BaseItemProviders` rows) — never use it for ID writes.

(e) MANDATORY 4-field exit gate — no ingest is complete until the item scores 4/4. Re-read via `GET /Items?Recursive=true&IncludeItemTypes=Movie&searchTerm=<Title>&Fields=Path,ProviderIds,ImageTags,Overview,ProductionYear` and confirm: (1) `ProviderIds.Tmdb` present, (2) `ProviderIds.Imdb` present, (3) `ImageTags.Primary` present, (4) `Overview` length > 50 chars (cast/crew arrive with the metadata fetch). If any field is missing after ~25s, wait 30s and re-read once (image download can race the DB write); if still missing, re-fire the per-item Refresh once more, then re-read. Hand over only with the 4/4 score quoted (Tmdb id + Imdb id + image keys + overview length); if a field cannot be filled (e.g. episode-parts in a Movies-type library where TMDB matching is ambiguous, or a title with no TMDB entry), report exactly which field is missing and why — never silently hand over a 3/4 as complete.

(f) Batch lesson (verified 11 Sep 2026, ~30-title ingest): clean `Title (Year)` names + stacked `-partN` files usually SELF-IDENTIFY on the library-scoped Refresh — always re-read IDs after the refresh BEFORE doing a manual TMDB POST, since the manual write is often unnecessary (Murder by Contract and the Notorious Criterion both auto-attached Tmdb+Imdb+art with no POST). When auto-match picks the WRONG variant (American Revolution row matched 'An Inside Look' instead of the Ken Burns series), correct the Name and lock it via `LockedFields:["Name"]`. Titles with no TMDB entry at all (7/27 in the batch) still get posters from a refresh once a clean Name + ProductionYear is POSTed — write those two fields even when IDs don't exist. For batches, report a per-title table: src size, dst path, decode RC, JF row, 4-field score, torrent hash + delete-readiness.

5. **Prompt for library placement: film / film noir / documentary — unless the user delegated the call.** After metadata is attached, ask the user which library the title belongs in before finishing — a title can live in Films, Film Noir, Documentaries, Music Docos, or dual-placed via hard link (same inode, zero extra disk: copy to one library, `ln` into the other, e.g. Sunset Boulevard / Chinatown). Never assume placement from genre alone. Music Docos convention is one folder per title (`Title (Year)/` holding the film plus art) while Documentaries mixes loose files and folders — so a move into Music Docos means creating the folder and hard-linking the file into it, not dropping a loose file; follow with a library-scoped Refresh of that library only and verify the new row before touching the source entry.

Deleting on-disk alternate cuts (`.orig.mkv`, `.remux-backup.mkv`, `.recode.mkv`) after the live file is confirmed leaves their Video rows as harmless dead entries — offer a purge as opt-in, never rescan to clean them when ghost-preservation is in force. Same for superseded quality rips: when a higher-quality replacement verifies (probe + decode + JF row), delete the older rip so only the keeper remains — this user prefers replace, not keep-both — but keep the original until playback of the replacement is confirmed.

Do NOT purge dead rows with API `DELETE /Items/{id}` when the media mount is read-only — the server attempts a filesystem delete of the containing folder and returns 500 (`Access to the path ... is denied`); the failure is non-destructive (rows and disk both survive, verified by re-read) but the error is misleading. The only purge path is a staged SQLite delete — stop container, dual-backup the DB, delete the Video rows plus their `BaseItemImageInfos`/`MediaStreamInfos`/`UserData`/`AncestorIds` link rows, `PRAGMA integrity_check` must return ok, swap in, restart — and it needs explicit user approval like any live DB swap.

Multi-part films use Jellyfin's stacked convention, not versions or merges: one folder `Title (Year)` holding `Title (Year)-part1.mkv`, `Title (Year)-part2.mkv` (supported part tokens: cd/dvd/part/pt/disc/disk). The scanner stacks the parts into a single Movie row on a library-scoped Refresh of that library. When the user wants one entry per series in a Movies-type library, use the same stacked `-partN` naming — `S01E01` tokens create one Movie row per file and do NOT stack. Give the folder the clean title plus year and leave release-style tokens behind in the download dir — clean names auto-identify metadata and art with no manual Apply.

Documentary series living in a Movies-type library does NOT behave like TV: `S01E01` filename tokens do not group or stack — the scanner creates one Movie row per file, all sharing the same series title. Present it as one folder with clearly-titled parts instead: distinct per-part `Name` (`<Episode Title> (Part N)`) plus a per-part `Overview` locked via `LockedFields: ["Name","Overview"]` so rescans keep them. Ingest available parts immediately with Part N in the title rather than holding them for a complete set. Write per-episode `.nfo` + `tvshow.nfo` files alongside as a portable backup, but do not rely on them — a Movies-type library ignores `episodedetails` season/episode tags. When consolidating duplicate source folders into one canonical folder, delete the old folders natively then run a library-scoped Refresh of that library only — the pass purges rows whose paths no longer exist while keeping the new rows; verify by DB re-read because the UI can lag a running scan and briefly hide the series. Metadata-write path that works: `GET /Users/{uid}/Items/{itemId}` for the full DTO (bare `GET /Items/{itemId}` 400s on this build even with a valid key), mutate Name/Overview/LockedFields on the full object, then `POST /Items/{itemId}` with the whole DTO back (204). `POST /Items/RemoteSearch/Apply/{id}` 400s for this purpose — do not use it for manual title/overview edits. Use the lowercase-dashed Id form returned by `GET /Items?searchTerm=` for writes; verify with a DB re-read of Name/Overview, not the POST status alone.

## Agent control surface — REST API first, MCP for routine ops

The server exposes a full REST API on :8096 — prefer it over SQLite surgery whenever the server is healthy. Full verified endpoint map (auth headers, sessions, playback control, search, volume, ticks): `references/rest-api-agent-control.md`.

Fast facts, verified live 11 Sep 2026 on 10.11.11:

- **Auth header that works:** `Authorization: MediaBrowser Token="<key>"` (200 on `GET /Sessions`). Credentials are in `/root/.hermes/.env` as `JELLYFIN_URL` + `JELLYFIN_API_KEY` — read them into shell vars, never echo the key. API keys cannot hit `/Users/Me` (400), so always pass an explicit userId.
- **Liveness:** `GET /health` → `Healthy` (no auth, and cheapest check). `GET /System/Info/Public` needs no auth either.
- **Verify before you act:** `GET /Sessions` first, every time; a session id is a 32-char lowercase hex string, a different namespace from (dashed UUID) item ids — read it live, never infer it. Only drive a session advertising `SupportsMediaControl: true` with your command in its `SupportedCommands`. A `404` from a control call means that session id went stale — re-read the list rather than retrying the same id; a `401` means the key is wrong/revoked, and **API keys have no refresh flow**, so do not blind-retry.
- **Two snippets that are wrong and get copied around:** playback is `POST /Sessions/{id}/Playing?playCommand=PlayNow&itemIds=<uuid>` — **query params, not a JSON body**; and volume is `POST /Sessions/{id}/Command` with body `{"Name":"SetVolume","Arguments":{"Volume":"50"}}` — there is no `/Command/VolumeLevel` route. Ticks: 1 s = 10,000,000.
- The `jellyfin-apiclient-python` package (`import jellyfin`) is NOT installed here; use curl/requests rather than assuming it exists.

User-state fixes have a dedicated endpoint (`POST /Users/{userId}/Items/{itemId}/UserData`) — use it for resume/played/favorite updates instead of stopping the container for a DB write. If the docs path 404s on a given build, the API itself is still complete; fall back to the canonical spec (`https://api.jellyfin.org/openapi/jellyfin-openapi-stable.json`) for codegen.

MCP wrappers (stdio transport, API-key env vars) cover routine operations only: status, library scan triggers, users, sessions/playback control, item search, scheduled tasks, activity log. Use them for scan-this-library, stop-that-session, what-is-playing checks. They do NOT reach the forensic half of this skill — SQLite ghost reconciliation, container-flag fixes, filesystem remux verification — which stays in the shell/SQLite/ffmpeg workflow. Weigh any MCP server on always-loaded tool count versus context cost before installing; gateway restart is required to discover new tools.
