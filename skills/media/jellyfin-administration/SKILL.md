# Jellyfin Administration

Operate the homelab Jellyfin server: Docker inside an unprivileged LXC (CT105 `jellyfin` on prox2, `192.168.214.109`), media over CIFS mounts (rw on the GUH share — in-Jellyfin deletion is enabled), multiple libraries that deliberately scan overlapping folders, Intel N150 iGPU for transcoding. Jellyfin is unusually sensitive to *how* it is moved — the SQLite DB encodes absolute media paths, user accounts and watch state, and schema migrations run as one giant transaction that can wedge for hours.

## When to Use

- Playback fails, stutters, plays the wrong audio/subtitle track, or resumes wrongly; a client reports a "fatal player error".
- Adding, replacing, renaming or auditing library files (ingest, ghost repair, TMDB metadata).
- Deploying, moving or upgrading the server; diagnosing a wedged DB migration.
- Controlling sessions (play / pause / seek / volume), searching the library, reading or resetting user state.
- Recovering an admin password.

## Golden Rules — read before any task

1. **Never run a library-wide rescan.** Ghost rows are a deliberately-kept "films I need to replace" list and a full rescan purges them. Use a **library-scoped Refresh of ONE library** (`POST /Items/{libId}/Refresh?Recursive=true`, both ReplaceAll flags false).
2. **Write media natively on the SMB server** (`proxmox3:/mnt/<share>/videos/...`). The prox1 `/srv/files/...` view and the container's `:ro` mounts are read-only — renames, copies and remuxes there fail. Never mount a rescue image as a second library source.
3. **DB edits are the exception, not the method.** Only two rewrites are sanctioned: the single-row path/stream swap, and the dead-row purge. Both go: stop container → dual-backup `jellyfin.db` (`/tmp` + `config/data/SQLiteBackups/`) → edit a staged copy → `PRAGMA integrity_check` must return `ok` → swap in, delete `-shm`/`-wal`, restart. **Always get explicit user approval before a live swap.** If the container must stay up (playback in progress), never `cp` the live db file — it misses `-wal`/`-shm` and the snapshot is stale; snapshot with `sqlite3 jellyfin.db ".backup <snap>"` and `integrity_check` the snapshot instead.
4. **Prefer the REST API over SQLite** whenever the server is healthy.
5. **Never swap a media file while any client has it open — even if `/Sessions` shows no `NowPlayingItem`.** A player keeps serving its own byte offsets: replace the file underneath it and every later range request reads NEW bytes at OLD offsets, so the picture corrupts from that instant onward. It looks exactly like an encode defect ("the recode broke the video from 09:20") while the file is perfect. `/Sessions` reporting `NowPlayingItem: None` does NOT mean idle — a paused/stalled player shows that way. Before any in-place swap, cross-check today's log for a `started playback of '<title>'` line without a matching `stopped playback` (proven 21 Oct 2026: a swap at 07:23 NZ landed inside a session that had started at 06:46 and only closed at 07:53; the user saw corruption from 09:20 — the point they reached at swap time — and the recode itself measured SSIM 0.99, identical cadence and 0 decoder errors). After a swap that may have straddled playback, have the client back out of the player and play fresh — never resume the stalled player, and verify with a decode at the reported timestamp through `/Videos/{id}/stream?static=true` rather than from disk. **Enforced in code now:** `media_lib.jellyfin.is_playing(item_id)` reads `/Sessions` for a matching `NowPlayingItem.Id`, and `cli/apply.py` skips (rather than fails) any row it reports as playing so the next apply run retries it — this is a floor, not the whole rule: a paused player still reports `None`, so keep the log cross-check for anything the guard cannot see.
6. **A completed copy is never proof of playability.** Verify through the container path — probe, mid-file decode, `dd` read.
7. **A "nothing new in the logs" playback failure is client-side.** Hard-refresh the client and Play fresh — never resume a stalled player — and do not re-edit the DB or encoder settings.
8. **Codec house rules — encode h264; keep incoming 1080p HEVC as-is; never encode *to* AV1, MPEG-2 or MPEG-4 Part 2.** The N150 cannot hardware-ENCODE AV1, and the legacy codecs are the ones causing failures. Before choosing a container or proposing a remux, read `references/container-and-codec-policy.md` — a container change is a free stream copy but it can never fix a codec a client cannot decode, so check the codec first.

## Agent control surface (REST API :8096)

Full verified endpoint map — auth headers, endpoints, status codes, session-safety rules: **`references/rest-api-agent-control.md`**.

- **Auth:** `Authorization: MediaBrowser Token="<key>"` (verified 200 on `GET /Sessions`). API keys cannot hit `/Users/Me` (400) — always pass an explicit `userId`. `X-Emby-Authorization` is mandatory on `/Users/AuthenticateByName` and harmless elsewhere.
- **`GET /Sessions` first, every time.** Session ids are 32-char lowercase hex — a different namespace from (dashed UUID) item ids, so read them live and never infer one. Only drive a session advertising `SupportsMediaControl: true` with your command in its `SupportedCommands`.
- **Two snippets that are wrong and get copied around:** playback is `POST /Sessions/{id}/Playing?playCommand=PlayNow&itemIds=<uuid>` — **query params, not a JSON body**; volume is `POST /Sessions/{id}/Command` with `{"Name":"SetVolume","Arguments":{"Volume":"50"}}` — there is no `/Command/VolumeLevel` route. Ticks: 1 s = 10,000,000.
- **Status codes:** `404` on a control call = stale session id, re-read the list. `401` = key wrong/revoked, and **API keys have no refresh flow** — do not blind-retry. `204` = accepted, not confirmed.
- **An EMPTY response body is a busy server, not a bad query — retry it.** While a scan or refresh backlog is draining, `/Items` calls intermittently return nothing at all, and a piped parser dies with `json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)` or a bare `Invalid data found`. A 200 with zero bytes and a malformed response look identical to the shell. Wrap every read in a small retry helper (4-5 attempts, ~4 s apart) that returns `{}` on exhaustion, and branch on the emptiness explicitly (`get(...).get('Items', [])`) — otherwise a single busy moment reads as "no items", "series has no children" or "no matches", which are all wrong conclusions that send you down a repair path for a defect that does not exist. Same failure arrives mid-script: a multi-query loop that succeeds for the first few titles and then throws is the backlog, not the data.
- **User state:** `POST /Users/{userId}/Items/{itemId}/UserData` (e.g. `{"PlaybackPositionTicks":0}`) — fixes resume/played/favourite without stopping the container.
- The `jellyfin-apiclient-python` package is NOT installed here; use curl/requests. Canonical spec for codegen: `https://api.jellyfin.org/openapi/jellyfin-openapi-stable.json`.
- MCP wrappers cover routine ops only (status, scan triggers, users, sessions/playback, search, scheduled tasks, activity log). They do NOT reach the forensic half of this skill — SQLite ghost reconciliation, container-flag fixes, filesystem remux verification. Weigh any server on always-loaded tool count before installing; a gateway restart is needed to discover new tools.

## Common failures & fixes

| Symptom | Cause | Fix |
|---|---|---|
| Playback dies instantly; transcode log ends `No usable encoding entrypoint found for profile ...` then `Conversion failed!` | **Cause A** — `AllowAv1Encoding=true` on an N150 iGPU that can DECODE but not ENCODE AV1 | `AllowAv1Encoding=false`, `AllowHevcEncoding=true`, keep av1 in `HardwareDecodingCodecs`; probe with `scripts/vaapi-encode-probe.sh` — never trust a UI checkbox |
| Same player error; log ends `Error opening input: Invalid data found when processing input` | **Cause B** — the extension lies about the container (mkv bytes named `.avi`), forcing the wrong demuxer | extension must match the real container (mkv `1a 45 df a3`, avi `RIFF`); rename natively on the SMB server |
| Same error persists AFTER the rename; log now `No such file or directory` on the OLD name | **Cause C** — the DB row still points at the old filename | staged single-row DB swap (Golden Rule 3, approval required); detail in `references/playback-and-repair.md` |
| Playback fails but NO new transcode log or itemid lines appear | the attempt never left the client — it holds stale stream URLs | client-side: hard-refresh, back out, Play fresh; do not touch DB or encoder settings |
| "It won't play" (black screen / spinner) on ONE title, yet the server log is CLEAN and shows a healthy `-codec:v:0 copy` DirectStream | **Cause D** — the video is **MPEG-4 Part 2 (DivX/XviD)**, which browsers and most clients cannot decode; DirectStream passes it through untouched, so the server succeeds while the client renders nothing | re-encode to h264 — recipe, aspect-ratio trap, sample-encode rule and measured speeds in `references/playback-and-repair.md`. Probe EVERY file in the set (a mixed h264/mpeg4 set is normal), and note Jellyfin chooses DirectStream vs transcode inconsistently for these, so one good playback proves nothing |
| Plays fine but the client will NOT fast-forward/seek on one title while its neighbours in the same folder seek normally (Android/TV app, no transcode log, file probes clean) | the MKV's **leading SeekHead carries no Cues entry** — it chains to a second SeekHead that holds the real index. Media3/ExoPlayer's `MatroskaExtractor` records `cuesContentPosition` ONLY from a Seek entry whose SeekID is `1c53bb6b` (chained SeekHeads, Tracks and Tags are ignored: `if (seekEntryId == ID_CUES) cuesContentPosition = …`), then at the first Cluster falls into `SeekMap.Unseekable` — the source comment reads "Allow playback, but disable seeking." ffmpeg/VLC/mpv DO follow the chain, so the file probes, transcodes and direct-plays perfectly and only the phone/TV player is crippled | audit the FIRST 400 bytes of every file — parse the Segment's leading SeekHead and look for a `1c53bb6b` Seek entry (1642 of 1646 library mkvs had one; `Later with Jools Holland S68E06` did not, and two Travel Man + Grace S01E01 shared the defect). Fix in place with `scripts/mkv-seekindex-audit.py --fix`: it rewrites ONE Seek entry (prefers the Tags pointer, never Tracks) at identical byte length, so file size, mtime, DB row and play state are untouched; first 8 KiB backed up to `/root`; rollback on failed verify. Then prove it: pointed offset must hold `1c 53 bb 6b`, the cue cluster positions must land on `1f 43 b6 75` (they are segment-relative — add the segment data-start offset), and ffprobe `-read_intervals` must return pts at the target. A mkvmerge remux regenerates a valid SeekHead too but is a new file/probe; a **re-encode never fixes this**. EBML gotcha: a size vint's length is the number of LEADING ONE BITS of its first byte (`0xC2` = 2-byte vint), not a single marker bit — parse it wrong and every element after the first reads as garbage, which looks like "the index is corrupt" |
| Direct-play judders with zero transcode log | off-spec timebase (`23.975986` vs `24000/1001`), or CIFS read stalls on a contended spindle | probe `r_frame_rate,avg_frame_rate`; stream-copy remux with `-video_track_timescale 24000 -r:v 24000/1001`; if still bad, libx264 recode overnight |
| Slow start on direct play, no transcode log, repeated `MediaInfoHelper` + `Playback stopped` lines | the client is retrying a file that takes too long to OPEN — not an encoder problem | isolate per hop before touching any setting, **in this order**: (1) confirm which host actually runs the CT (`pct list` + `hostname` on each candidate — labels and IPs drift, and blaming the wrong host's load wastes the whole diagnosis); (2) faststart check by reading only the first 256 KB of the file and locating `moov` vs `mdat` (`moov` near offset 0 = faststart set; never `ffprobe -v trace` over CIFS, it reads the whole file and times out); (3) `PlaybackInfo` round-trip time, `dd` read on the share host, `dd` through the CIFS mount, encoder fps from the last real transcode log. A `dd` through the mount below single-digit MB/s while the share host reads hundreds of MB/s locally is a wedged client mount, not a slow server — recover per the CIFS-wedge rule in `media-path-safety` (D-state `cifs_call_async` workers confirm it), never by re-encoding the file. If every hop is fast, remux or replace the file (next row) — never tune the encoder for a startup stall. When one process looks guilty, divide its accumulated CPU minutes by wall-clock elapsed before calling it a runaway: ~78% of one core over 25 h is steady legitimate use (e.g. the fleet's shared local-LLM server), not a stuck loop — check what it serves before killing it |
| Batch AVI→MKV remux with originals to delete | unproven copies, and `ffmpeg -c copy` aborts on files with broken timestamps | remux with `mkvmerge` (it tolerates timestamp damage ffmpeg refuses), then gate EVERY file before deleting its original: probe-readable + audio/video stream-count match + duration ±2s + decode-sample 3 spans (start/middle/end) with `-xerror`. An extension swap is a NEW path = a new DB item: watched/resume states reset and Recently Added floods — batch per library and say so up front. ffmpeg also rejects non-standard temp extensions (`.mkv.new`): stage as `*.remux.mkv` and rename. Sweep for stale `*.remux-tmp.mkv` / `*.reenc-tmp.mkv` leftovers — plus intake staging extensions (`*.part`, `*.new`, `*.upnew`: a failed swap can leave a full-size staged copy inside the library folder) — the moment a batch ends and ALWAYS before any refresh — the scanner reads them as separate `Video` rows, so one leftover surfaces as a phantom duplicate of its title (two same-name entries, one pointing at the temp file). A `find <lib> -name '*.remux-tmp.mkv' -o -name '*.reenc-tmp.mkv'` returning anything is a failed cleanup, not a duplicate |
| Transcode segments to RAM | encoding settings are NOT in `/System/Configuration` (54 keys, none matching) | edit `config/config/encoding.xml` directly (`TranscodingTempPath`, plus `EnableThrottling=true` + `EnableSegmentDeletion=true` to bound RAM use), add a sized `tmpfs` mount in compose, recreate. Verify HW accel is actually engaged first: the `FFmpeg.Transcode-*` log command line names the encoder (`hevc_vaapi`) with end-of-run fps — 150+ fps means the encoder was never the problem |
| Movie row Path is a FOLDER, Size = first VOB, streams lead `dvd_nav_packet` | DVD-folder (VIDEO_TS) ingest — raw VOB chain, no IFO navigation | not an encoder issue; per-VOB probing + recode policy in `references/playback-and-repair.md` |
| A whole library section is imageless after remux batches | `EnableInternetProviders=false` + `SaveLocalMetadata=false` means art lived only in the cache keyed to old item IDs — new files have nothing on disk to fall back on | do NOT flip internet providers on globally: Jellyfin fuzzy-matches obscure rips to wrong titles. Repair controlled: strict TMDB match (exact-normalized title ≥85 accept, 60–84 hand-verify, below leave), save `poster.jpg`+`fanart.jpg` beside the media (folder-based) or `<basename>-poster.jpg` (loose files in the library root — verified honoured), frame-grab (`ffmpeg -ss <s> -frames:v 1`) where no database entry exists; when TMDB holds the title but carries no art/overview (proven: TMDB tv/6614 `When Disco Ruled the World` — one-line overview, zero posters), use the title's Wikipedia page as the metadata source; for BBC-aired documentaries prefer the BBC programme page (`bbc.co.uk/programmes/<pid>`) — it carries the authoritative synopsis, studio (BBC Four), runtime, producer credit and contributor list plus the official episode still for `poster.jpg` (proven: b00vfhyc `The Man Who Recorded America: Jac Holzman's Elektra Records` — TMDB had zero hits in both namespaces; overview/studio/year/cast/director → local `movie.nfo`, BBC still → `poster.jpg`, frame-grab → `fanart.jpg`; per-item full refresh verified: 689-char overview, BBC Four studio, poster + backdrop) (overview/studio/year/cast/director → local `movie.nfo`, which the scanner reads even with `SaveLocalMetadata=false`; never copy a TV-namespace TMDB id into a Movies-library nfo — the TV/movie id namespaces collide and the library resolves the wrong side — IMDb id only). when that happens, write the overview through the API DTO and lock it instead of firing more refreshes — a sidecar `<plot>` is not a reliable write path for a row that has just been rebuilt, web-found promo still or frame-grab for `poster.jpg`, series-level `poster.jpg` for season art (imageless season rows then inherit in clients — cosmetic), hand-reject lookalikes, library-scoped Refresh, recount to prove the drop |
| Item lost its poster/art after a rename | the scanner deleted the old row (images with it) and created a fresh one | re-attach IDs then per-item Refresh with `ReplaceAllImages=true`; never a full rescan. For path-change swaps (remux/re-encode) there are no IDs to re-attach: local art files (`poster.jpg`, `fanart.jpg`, stem-matched sidecars) carry over untouched — only remote-cached art is lost, and it returns via library-scoped image refresh. Verify `SaveLocalMetadata=false` on the library first so the refresh cannot overwrite locals |
| Deploying chosen artwork onto rows (poster swaps, person headshots) | `POST /Items/{id}/Images/Primary` takes the image **Base64-encoded** — raw bytes 500 with `FormatException` in `FromBase64Transform` (the controller reads the body through a Base64 CryptoStream). Send `base64.b64encode(data)` with `Content-Type: image/jpeg`, expect 204; proven Oct 2026. Sidecar route also works `poster.jpg` beside the media in folder items, `<basename>-poster.jpg` for loose files (basename must match the media filename exactly, including part tokens), `folder.jpg` inside the `metadata/People/<letter>/<Name>/` dir for person headshots (reach it through the server process's own mount namespace via `/proc/<pid>/root/...` when the admin shell lands in a different one). Then `DELETE .../Images/Primary` + per-item Refresh with DEFAULT modes — an image-mode FullRefresh fetches provider art and overwrites the sidecar. Prove adoption by downloading the served image and byte-comparing against the placed file (`ImageTags` only names the slot; a size mismatch is remote art, not a resize) |
| A single unrelated picture follows the user across every library screen | a stray `fanart.jpg` (or `poster.jpg`) sitting at the **library root** was adopted as the library-level Backdrop — check `/Items/{libId}/Images` for a Backdrop entry and byte-compare against root files | delete the root file, `DELETE /Items/{libId}/Images/Backdrop`, verify the slot is gone; audit every library root for strays while there |
| Cannot tell by tags whether a refreshed row actually adopted new sidecar art | `ImageTags` only names the slot (`Primary`), never the bytes — a refresh that silently kept the old image reads identical to one that applied the new poster | after any artwork change, download the served image (`GET /Items/{id}/Images/Primary`) and hash-compare it against the file placed on disk; equality is the proof, tag presence is not |
| New sidecar `.nfo`/poster files sit unread after a library-scoped Refresh, even with FullRefresh+ReplaceAllMetadata | the library refresh does not reliably re-read sidecars added after first scan | apply per item: `POST /Items/{id}/Refresh?Recursive=true&MetadataRefreshMode=FullRefresh&ImageRefreshMode=FullRefresh&ReplaceAllMetadata=true` (`ReplaceAllImages=false` keeps curated art), then re-read Overview/ImageTags. | Item still reports the OLD codec after a file was swapped in place (same path, new bytes verified on disk) | the row's `MediaSources` stream info is cached — a library-scoped Refresh re-resolves metadata for known rows but does not re-probe the file | disk is ground truth: ffprobe the file first; then per-item Refresh with `MetadataRefreshMode=FullRefresh` to force a re-probe, and only then re-read `MediaSources`. A stale codec reading after a swap is a cache, never proof the swap failed | the row's `MediaSources` stream info is cached — a library-scoped Refresh re-resolves metadata for known rows but does not re-probe the file | disk is ground truth: ffprobe the file first; then per-item Refresh with `MetadataRefreshMode=FullRefresh` to force a re-probe, and only then re-read `MediaSources`. A stale codec reading after a swap is a cache, never proof the swap failed |
| Hand-built series rows (no usable TMDB/TVDB entry, or provider data known-wrong) lose episode names/overviews on refresh, or episode NFOs sit ignored | provider-matched series rows resolve episodes from the provider, not local NFOs — and a series-level Refresh with `ReplaceAllMetadata=true` re-applies provider data over EVERY episode, wiping hand-written NFO content library-wide (proven: Abbey Road S2 took TMDB's wrong identities; Sound/Rock and Roll America lost all episode overviews in one call) | never series-level ReplaceAll on a hand-built series. | A freshly-placed episode comes back named for a DIFFERENT episode (proven 22 Oct 2026: the Elvis file landed on a row renamed "Judas Priest: British Steel"; the Petty file on "Peter Gabriel: So") | placing a file into a **ghost** row (no `Path`) triggers a fresh provider lookup for that slot, and the lookup keys on the **episode number** — while this library uses *scene* numbering and TMDB differs (Elvis = library S03E05 but TMDB S03E06; Petty = library S10E02 but TMDB S09E02). The damage is exactly one slot off, and `Name`, `Overview`, `PremiereDate`, `ProductionYear` AND `ProviderIds` are all overwritten. Ghost rows carry no `LockedFields`, so nothing protects them, and the refresh runs async — the wrong name can appear after the placement already looked successful | **automated:** `cli/ingest_new` now runs the name check itself after row discovery and prints `ROW-NAME-OK` / `ROW-NAME-MISMATCH` per item, appending any mismatch to `state/needs-your-check.json` and the journal (`event: row-name-mismatch`). Add `--fix-names --tmdb-series <id>` to repair automatically: it resolves the episode **BY NAME** on TMDB (never by number), rewrites `Name`/`Overview`/`PremiereDate`/`ProviderIds`, locks `Name`+`Overview`, and re-reads to confirm. The comparison lives in `media_lib/rowcheck.py` (shared, so the CLI and the audit cannot disagree). **Manual:** `scripts/audit_series_names.py [--search "<series>"]` audits a whole series and exits 1 on any mismatch — run it after any placement batch |
| A torrent that is plainly in the queue is not found by name (`'Stevie Wonder' in name` → False for `Classic-Albums-Stevie-Wonder-...`) | separators differ between the queue's name and your query: hyphens, dots and spaces are all the same title | normalise before comparing (`re.sub(r'[^a-z0-9]+',' ',s.lower())`); centralise it as `qb.find_torrent(fragment)` rather than a raw substring test — this bit three times in one session (torrent lookup, SAB history match, episode identification) |
| Placement fails `STAGE=SRC-MISSING` although the file is on disk | qBittorrent's `content_path` is a **FOLDER** for multi-file torrents, and `torrents/files[].name` is relative to `save_path` — so joining them produces `/<folder>/<folder>/<file>` (a doubled path) | resolve to the largest video inside before placing (`qb.resolve_media_path(content_path, hash)`); never hand-join `content_path` + `name` |
| `media_scan` keeps re-offering releases that were already ingested | two ledgers existed: `media_scan` consults `jellyfin-ingest-ledger.json` while the placement stage journaled only to `ingest-new.jsonl`, so the scan never learned about it | record `{hash, dest, action:'place'}` into the SAME ledger the moment a placement succeeds (`safety.record`), and look the hash up by path when the spec omits it (`qb.torrent_for_path`) |
| A placement is journaled but its Jellyfin row never appears (or appears only minutes later) | the first `POST /Library/Media/Updated` is sometimes dropped while the scan queue is busy — the log shows no `will be refreshed` line for the path | re-notify after a poll budget rather than treating one 204 as delivery: notify → poll ~60 s → notify again. Prove arrival by exact `Path` equality, never by a name search |
| One SABnzbd slot is `Failed` yet carries a storage path and a full size | `fail_message` taxonomy decides retryability, and a storage path does not mean the payload is intact | `Repair failed, not enough repair blocks (N short)` with small N (≤10) is worth exactly ONE retry (`sab.retryable_failures()`); `Aborted, cannot be completed` never is — the backbone lacks the articles and retries only spend block data |
| New files on disk are still absent after a library-scoped `POST /Items/{libId}/Refresh` | that endpoint re-resolves metadata for KNOWN rows — it does not discover new files on disk | discover new files with the `RefreshLibrary` scheduled task (`POST /ScheduledTasks/Running/{id}`), exporting the ghost list first; for a single file prefer surgical `POST /Library/Media/Updated` with `{Updates:[{Path, UpdateType:"Created"}]}` (proof recipe in the deletion section above). If files are STILL absent after discovery, check the log before concluding they were skipped: `grep "will be refreshed" config/log/log_YYYYMMDD.log` for the folder — a hit means the refresh backlog (hundreds of folders, drained sequentially) has not reached it yet, and re-firing Created updates while queued is a no-op. Genuinely-skipped classes need no retry: files under `Extras/` (attached as extras, no rows by design), `*-Sample` (ignored by rule), and dot-prefixed names (the scanner ignores hidden files — a `Created` ping 204s and the row never appears, so name probe/test files without the leading dot) |
| A just-ingested title "verifies" by name search, yet the row predates the ingest | a same-name row from an EARLIER ingest (or an old ghost) matches the search and masquerades as the new file — name search cannot distinguish them | verify by **DateCreated + exact Path**, never name alone: the row's `DateCreated` must be today and its `Path` the file just placed; a same-name row dated months back is the old ingest, not proof the new file landed |

## Core procedures

1. **Is it up?** `GET /health`; then `GET /System/Info/Public`; `docker ps` shows `Up ... (healthy)`.
2. **Torrents stalled / the source is dead** → `references/qb-stalled-revival.md` FIRST (check the `max_active_downloads` queue cap and refresh the tracker list — most "dead" torrents are local misconfiguration, not dead swarms), then `references/torrent-source-recovery.md` to prove swarm death. Never recommend a replacement on an index's seeder count alone.
3. **Ingest a new file or a ghost replacement** → `references/ingest-and-intake.md`. Three checks before handover (extension = real container; MP4 `mov_text` remux rules; audio-default audit), then TMDB IDs and the mandatory 4-field exit gate.
4. **Playback fails, judders, or plays the wrong track** → `references/playback-and-repair.md`.
5. **Deploy, move, upgrade, or a wedged migration** → `references/deploy-migrate-and-audit.md`.
6. **Ghost items / library content audit** → `references/deploy-migrate-and-audit.md`.
7. **Duplicate media audit or removal** → `references/duplicate-detection.md`. Prove separate inodes AND identical content before removing either name, re-prove it at delete time, then refresh only the libraries that lost files and verify by exact path.
8. **Admin locked out** → `references/password-recovery.md` (short form below).
9. **Library quality sweep — what is too low-resolution, what needs recoding** → `references/library-quality-sweep.md`, runnable as `scripts/library-quality-sweep.py`. One REST pass, no `ffprobe`. A sweep has **two** outputs (redownload candidates and recode candidates) and both must be reported; never let an unrelated mid-turn blocker swallow half of it.
10. **Sourcing the higher-resolution replacements** → `references/upgrade-sourcing.md`. Expect the null to dominate and name the structural reason (SD-only broadcast era, late HD series start, DVD-only series); fan the list out one chunk per subagent with namespaced scratch files, aggregate from the result **files** not the summaries, and grade each find hard/soft/different-programme (matching on the held file's identity, not title+year) before recommending a download. Then add the accepted batch to the downloader with the queue cap sized to the batch **first**, and report an alive/dead split rather than a success count — `references/qb-stalled-revival.md`. Number the shortlist so the user can select by number (they reply with numbers, e.g. "skip these three, add the rest") and give the unique-download count alongside the row count once duplicate rows are collapsed.
11. **Audit series and how they are represented** → `references/series-structure.md`. Group by parent folder AND by episode-marker stem (`Limit=0` returns zero items — paginate), excluding the library root, then classify each series as a **part-series** (one work in N parts → `PartCount`) or an **episodic series** (N distinct programmes → one entry per series). Report episode count vs entry count per series before restructuring: `MediaSources > 1` with `PartCount = None` is an accidental version-group, not a successful combine. When the target is a Shows library, the audit has a **second output** — per-episode metadata coverage — so run `scripts/series-metadata-audit.py` alongside it and report both: the structure can be perfect while older series carry overview/date gaps a repair pass should fill.
12. **Container or codec strategy — "should I remux this to MP4?", "what should the library standardise on?"** → `references/container-and-codec-policy.md`. Check the CODEC before the container: a remux is a free lossless stream copy that can never make an undecodable codec play. Remux to MP4 only when the video is h264/vp9/av1 AND the audio is browser-safe (aac/mp3/opus — **not** ac3/eac3/dts) AND there is no image-based subtitle track **unless the media is English** (subtitle compatibility is not a priority for English material; it is the whole point for non-English). Otherwise keep MKV and fix the codec. Probe the actual client with `canPlayType` rather than trusting a published codec table. Measure the split before advising, and when the legacy-codec set overlaps the low-resolution set, recommend REPLACEMENT over recoding — a recode locks the low resolution in.
13. **The torrent backlog — batch intake without an agent** → `/root/.hermes/scripts/jellyfin-media-intake.py` (deterministic, `--dry-run` by default, `--apply` to act). Once intake is a script the per-run row cap that existed only to keep agent prompts short is obsolete: bound a run by an **estimated-time budget**, not a row count, and **measure** the copy throughput instead of assuming it. Never run it while another intake process is mid-flight, and never let it delete an old file before the NEW file's own content tag has been checked against the target item. Full contract in `references/ingest-and-intake.md`. Its scanner module (`jellyfin-new-media-scan.py`, loaded via importlib — the filename is hyphenated so a plain import is impossible) owns the proven title normalizers (`norm_tokens`, `squash`); any new batch-matching script must reuse those rather than hand-rolling its own, or the two slowly disagree about what a title is.
14. **Batch metadata fill without destroying existing metadata** — repairing a whole library section (imageless / ID-less rows) after a remux/recode batch. Snapshot every row (`Id,Name,Year,Path,ProviderIds,ImageTags,Overview` length) to JSON first — that file is the rollback reference, not a log. Classify the 4-field exit gate per row and **exclude 4/4 rows from every write in the pass**; a good row can only lose. Exclude the exact file paths a concurrent batch still owns (derive them from its queue, never from memory), but skip the file, never its whole folder — a per-item Refresh targets one item id and neighbours are unaffected. Parse that queue by splitting on its size token: a `\S+` path capture truncates at the first space in release-named files and the exclusion silently misfires. Accept a TMDB match for unattended writes only on squash-exact title (row Name first, parent folder name as fallback when the row carries release tokens — folders are usually clean) + year ±1 + non-empty provider overview; this is deliberately tighter than the single-item ≥85 rule, because no human reads the match before it lands. Route fragments (`.f251`/`.temp` yt-dlp debris), stacked part-rows, year-less rows and near-misses to a check list, never through. For brand-new rows, refresh-first-then-write: the user-scoped item endpoint returns 400 until the server has probed the file (no `MediaSources` yet), so fire per-item Refresh, wait for a stream to appear, and only then fetch the DTO for the full-DTO round-trip. That same Refresh runs the provider search, which on clean `Title (Year)` names usually attaches the correct IDs by itself — re-read first and hand-write only what is still missing or wrong. Write IDs through the full-DTO round-trip with no `LockedFields`, per-item Refresh with both ReplaceAll flags false, then re-read every touched row against the gate and recount the library gap. If a write replaced a pre-existing Imdb, resolve the OLD value through TMDB `/find/{imdb}` before calling it damage — an id with no TMDB record anywhere was stale data, and the overwrite was the fix. Journal each ID write the moment it lands — the same per-item rule as the intake ledger — because a crash between the last write and an end-of-run dump otherwise loses the record of what changed.

### Enabling real in-Jellyfin media deletion (verified 12 Sep 2026)

Deletion is blocked by **two independent layers**, and BOTH must be fixed. Fixing one and re-testing looks like the fix "didn't work".

1. **Filesystem** — the write chain is four hops and every hop must be rw:
   `fstab` (proxmox1 `/srv/files/dguh`: `ro` -> `rw`) -> **CT restart** -> compose volume (`:ro` -> `:rw`) -> `docker compose up -d`.
   - A bind mount **snapshots** the source's ro/rw at container start: remounting the host source does NOT change an already-running container's view. `mount -o remount,rw /mnt/media` inside the CT fails `permission denied` (unprivileged CT), and `nsenter` from the host fails `must be superuser`. **Only a CT restart re-creates the bind**, and only `docker compose up -d` (not a plain restart) re-creates the container with new volume flags.
   - Verify with a write+delete loop inside the container over `/data/movies`, `/data/tvshows`, `/data/documentaries`, `/data/musicdocos`, `/data/filmnoir` — do not trust `mount` output alone.
2. **Jellyfin permission** — user policy `EnableContentDeletion=true` (+ `EnableContentDeletionFromFolders: []`) via `POST /Users/{userId}/Policy`.
   The flag is **per user, and only useful inside the libraries that user can see** (`EnableAllFolders` / `EnabledFolders`). A user with deletion enabled but a restricted library set cannot delete what is hidden from them, which reads as "the permission didn't work". Read `GET /Users` and confirm both the flag AND the library scope before concluding anything; verify the filesystem layer (above) rather than assuming the checkbox was the problem.

**There is NO per-library deletion option in Jellyfin 10.11.** `LibraryOptions` has no `EnableMediaDeletion` key (42 keys, none matching) — a POST to a library-options endpoint returns 204 and changes nothing, and re-reading shows `None`. Deletion is governed **only** by the per-user flag. Do not chase a library-level setting that does not exist.

- The library-options endpoint is **`POST /Library/VirtualFolders/LibraryOptions`** (singular `Library`) with `{Id, LibraryOptions}` — `/Libraries/Options` is a 404.
- End-to-end proof: drop a tiny real video into a library dir (`/usr/lib/jellyfin-ffmpeg/ffmpeg -f lavfi -i testsrc`), `POST /Library/Media/Updated` with `{Updates:[{Path, UpdateType:"Created"}]}`, poll `/Items?...SearchTerm=`, then `DELETE /Items/{id}` and check the file is gone from disk. Expect `204` and a real unlink. A transient extra item count right after the delete is normal — it clears on its own within ~a minute.
- Note `GET /Items/{id}` is a **400** — that route requires a userId in the path; use `/Items?...` search or a user-scoped route to read an item back.

### Password recovery (short form)

Jellyfin hashes passwords with PBKDF2-SHA512 — the original text can **never** be recovered (one-way, salted). Reset instead; full recipe in `references/password-recovery.md`.

- Usernames on this install: `root`, `emily`, `tv`, `mary`. **Admin: `root` only** (Permissions table: Kind=0 row with Value=1 = IsAdministrator). **Live-check with `GET /Users` — this list drifts** (a previous revision of this skill named `remote` + `kathleen`, both since removed). There is **no user called `admin`** — "give the admin delete permission" means `root`; when a request names an account that does not exist, report the real account list instead of creating one.
- Hash format (PHC string, **hex** not base64): `$PBKDF2-SHA512$iterations=210000$SALT_HEX_UPPER$HASH_HEX_UPPER`; generate with `hashlib.pbkdf2_hmac("sha512", pw, salt, 210000, dklen=64)` (hex upper), then `UPDATE Users SET Password='<hash>' WHERE Username='root'`. Back up the DB first — there is no undo.
- API login tests require the `X-Emby-Authorization` header, or the endpoint throws a bare stack trace instead of returning "invalid username or password".
- **If a user has since changed their own password, do NOT re-reset.** A later "Invalid username or password" is then expected — check the auth log for `Authentication request for "root" has succeeded` and compare `Users.Password` / the DB mtime against your backup. Ask the user for the new password rather than resetting over it.

## Decision briefs

Standing operator preferences (apply without re-asking): **software libx264 CRF 20** for all re-encodes — hardware VAAPI was measured and rejected for this library (bigger files at matched quality); **keep the higher-bitrate copy** when a smaller download duplicates a bigger library file, regardless of resolution labels; upgrades go **new file in, refresh, remove old** (never in-place overwrite); every movie ingest ships a **backdrop** (`backdrop.jpg` from TMDB alongside `poster.jpg`) — clients paint their background from the library's backdrops, so one lone `fanart.jpg` otherwise follows the user across every screen; destructive, structural, and metadata-judgement calls each get their own entry in the brief.

When presenting pending decisions, itemize EACH one with what it is, the options, and what happens either way — terse one-line summaries get rejected. Frame each decision as an explicit choice (Yes/No, or lettered options for pick-one-of-N) with a one-line explanation of what each option concretely does, recommended option first. **Number every question** so the user can answer by number. Number shortlists so the user can select by number (see procedure 10). For ingest batches, present the download-vs-incumbent comparison (codec, resolution, size, existing IDs, verdict per item) BEFORE acting, and act only on the approved subset. Destructive, structural, and metadata-judgement calls each get their own entry; never fold a delete, source, or placement decision into a passing mention.
